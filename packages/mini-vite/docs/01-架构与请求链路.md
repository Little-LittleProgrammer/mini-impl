# 架构与请求链路

这篇先建立全局心智模型:mini-vite 启动时做了什么,以及一次请求是怎么在各模块间流转的。读完这篇再去看单个插件,就不会迷失在局部细节里。

## 一、核心思路

传统打包器(webpack)在启动时把整个依赖图打成 bundle,项目越大启动越慢。Vite 的思路相反:

- **源码不打包**。浏览器原生支持 `<script type="module">`,每个 `import` 就是一个 HTTP 请求。mini-vite 拦截这些请求,按需把单个文件转换成浏览器能跑的 ESM 再返回。改一个文件只需重新转换那一个文件。
- **依赖才打包**。第三方依赖(如 `vue`、`pinia`)文件多、且常含 CommonJS,浏览器没法直接跑也不该逐个请求。所以启动时用 esbuild 把它们预先打包成单个 ESM 文件。

mini-vite 把这套思路压缩成最小实现,可以按职责分成六层:

```
1. CLI 与启动入口        cli.ts → server/index.ts
2. 开发服务器与中间件     connect + 三个中间件
3. 插件系统与插件容器     pluginContainer.ts + plugins/*
4. 模块转换链路          transformRequest.ts
5. HMR 与模块图          server/hmr.ts + client/client.ts
6. 依赖预构建            optimizer/index.ts
```

## 二、启动流程

入口链路:`bin/mini-vite.js` → `cli.ts` → `startDevServer()`(`server/index.ts`)。

`startDevServer()` 按以下顺序执行(对照 `server/index.ts:37`):

1. **创建 connect 应用**。connect 是极简的 HTTP 中间件框架,express/koa 的底层。
2. **注册插件数组**,顺序固定:
   ```ts
   const plugins = [
       resolvePlugin(),         // 路径解析
       esbuildTransformPlugin(),// TS/JSX → JS
       commonjsPlugin(),        // CJS → ESM
       importAnalysisPlugin(),  // 重写 import + 注入 HMR
       cssPlugin(),             // CSS → JS 模块
       hmrPlugin(),             // 提供客户端虚拟模块
   ]
   ```
   这个顺序很关键,决定了 transform 链的执行次序,后面 [插件系统](./02-插件系统.md) 会详细讲。
3. **创建插件容器** `createPluginContainer({ plugins })`。
4. **注册中间件**,顺序同样关键:
   ```
   indexHtmlMiddleware   →  处理 GET /,返回注入了 HMR 脚本的 HTML
   sirv(publicDir)       →  public 目录存在时,静态托管(/xxx 直接访问)
   transformMiddleware   →  处理 JS/CSS/import 请求,调用 transformRequest
   ```
5. **执行各插件的 `configureServer`**,把 `serverContext` 传给插件保存(`resolve`、`importAnalysis`、`hmr` 插件都依赖这一步拿到 server 引用)。
6. **创建 HTTP server**,并在其上创建 HMR 的 WebSocket 服务(`createHMRServer`),复用同一个端口。
7. **监听端口(3001)**,在 listen 回调里执行 `optimizeDeps()` 做依赖预构建。

> 注意预构建发生在 `server.listen` 回调中,也就是**服务已经能接收请求之后**才开始扫描打包。

## 三、请求链路:按类型拆解

服务起来后,浏览器访问 `http://localhost:3001/` 触发一连串请求。下面按请求类型逐一拆解。

### 1. `GET /` —— HTML 入口

命中 `indexHtmlMiddleware`(`middlewares/indexHtml.ts`):

1. 读取 `root/index.html`。
2. `injectHMRClient(html)`:在 `</head>` 前插入
   ```html
   <script type="module">
       import "/node_modules/.mini-vite/client.js";
   </script>
   ```
   这行脚本就是 HMR 客户端的入口。
3. 遍历插件执行 `transformIndexHtml`(当前内置插件都没实现,是预留扩展点)。
4. `Content-Type: text/html` 返回。

### 2. `GET /node_modules/.mini-vite/client.js` —— HMR 客户端

浏览器解析 HTML 后请求上一步注入的脚本,命中 `transformMiddleware`(`isJsRequest` 为 true)→ `transformRequest`:

1. `resolveId`:`hmrPlugin` 识别这个固定路径,返回 `{ id: '/node_modules/.mini-vite/client.js' }`(虚拟模块,不在磁盘上)。
2. `load`:`hmrPlugin` 返回预编译好的 `clientCode`(`configureServer` 阶段用 esbuild 把 `client/client.ts` 编译好缓存的)。
3. `transform`:hmr 插件无 transform,但会经过 importAnalysis 等(虚拟路径不含 mtime,不进缓存)。
4. `Content-Type: application/javascript` 返回。

### 3. `GET /src/main.ts` —— 业务 JS 入口

这是最完整的一条链路,命中 `transformMiddleware` → `transformRequest`:

| 步骤 | 调用 | 说明 |
| --- | --- | --- |
| 1 | `cleanUrl(url)` | 去掉 query 和 hash |
| 2 | `pluginContainer.resolveId('/src/main.ts')` | `resolvePlugin` 拼成磁盘绝对路径 |
| 3 | `getFileMtimeMs(id)` | 取文件 mtime,用于缓存校验 |
| 4 | 查 `transformCache` | id 相同且 mtime 未变则直接返回缓存 |
| 5 | `pluginContainer.load(id)` | `esbuildPlugin.load` 用 `fse.readFile` 读源码 |
| 6 | `pluginContainer.transform(code, id)` | 依次跑 transform 链(见下) |
| 7 | 写入 `transformCache` | 以 id 为 key,带上 mtime |

**transform 链的执行顺序**(由插件注册顺序决定):

| 顺序 | 插件 | 对 `.ts` 文件做什么 |
| --- | --- | --- |
| 1 | `esbuild` | TS/TSX/JSX → ESM JS |
| 2 | `commonjs` | 仅匹配 `.js/.cjs`,`.ts` 跳过 |
| 3 | `importAnalysis` | 重写每个 import 路径、注入 `import.meta.hot`、上报模块图 |
| 4 | `css` | 仅匹配 CSS,跳过 |

`importAnalysis` 是这条链的重点,它做三件事:
- **裸导入**(如 `import { createApp } from 'vue'`)→ 直接字符串重写为 `/node_modules/.mini-vite/deps/vue.js`(指向预构建产物)。
- **相对/绝对路径** → 调 `this.resolve()` 走 resolve 插件解析,再用 `fsPathToUrl` 转成浏览器 URL。
- 调 `hmr.updateModuleGraph(importer, importees)` 更新依赖图,并在模块顶部注入 HMR 上下文代码。

### 4. `GET /src/App.css` —— CSS 请求

`isCssRequest` 为 true → `transformRequest`:

1. `resolveId`:resolve 插件解析路径。
2. `load`:`cssPlugin.load` 读取 CSS 文本。
3. `transform`:`cssPlugin.transform` 把 CSS **转义成字符串**,包进一段 JS——这段 JS 在浏览器里创建 `<style data-vite-dev-id="...">` 标签注入页面,并带上 `import.meta.hot.accept/dispose`。
4. 返回的 `Content-Type` 是 `application/javascript`(注意:CSS 最终是以 JS 模块形式返回的)。

> mini-vite 的 CSS 处理**仅做转义注入**,不支持 CSS Modules、PostCSS、预处理器。详见 [与 Vite 的差异](./05-与Vite的差异.md)。

### 5. `GET /node_modules/.mini-vite/deps/vue.js` —— 预构建依赖

由 importAnalysis 重写后产生的请求:

1. `resolveId`:resolve 插件 `path.join(root, url)` 得到磁盘上的预构建产物路径。
2. `load`:esbuild 插件读取文件(预构建产物已是打包好的 ESM)。
3. `transform`:产物本身是 ESM,各插件基本无操作。
4. 返回 ESM 代码。

## 四、缓存机制

mini-vite 有两层缓存,都在内存里:

### transform 缓存(`transformRequest.ts:23`)

```ts
const transformCache = new Map<string, TransformCacheEntry>()
// TransformCacheEntry: { result, mtimeMs }
```

- **key**:`resolveId` 返回的绝对路径 id。
- **命中条件**:当前文件 mtime 与缓存记录的 `mtimeMs` 完全一致。
- **失效**:HMR 在文件 `change/add/unlink` 时调 `invalidateTransformCache(id)` 清除。
- 虚拟模块(如 client.js)没有 mtime,`getFileMtimeMs` 返回 null,不会稳定命中缓存。

### 预构建缓存

预构建产物落在磁盘 `node_modules/.mini-vite/deps/`。mini-vite 每次启动都全量重新构建,**没有** hash 校验或增量复用(Vite 有)。

## 五、各模块如何衔接

把上面串起来,完整的开发态闭环是这样的:

```
CLI 启动
  └→ startDevServer 创建 connect、注册插件、装配中间件
       └→ 创建 HTTP server + WebSocket(HMR)
            └→ listen 回调里执行 optimizeDeps 预构建依赖

浏览器请求
  GET /            → indexHtmlMiddleware → 注入 client.js 脚本 → 返回 HTML
  GET *.js/.ts/.css → transformMiddleware → transformRequest
                         └→ resolveId → load → transform(插件链)
                              └→ importAnalysis 重写 import + 更新模块图 + 注入 hot

文件变化
  chokidar 监听 → 失效 transform 缓存 → 按文件类型决策
       └→ JS:沿模块图算更新边界 → 发 js-update
       └→ CSS:发 css-update
       └→ HTML/其他:发 full-reload
            └→ WebSocket 推给浏览器 → client.ts 执行局部替换或刷新
```

读源码时,重点抓这几个接口就能串起全局:

- `Plugin`(`plugin.ts`):系统允许插件介入哪些阶段。
- `createPluginContainer`(`pluginContainer.ts`):插件钩子如何被串起来。
- `transformRequest`(`transformRequest.ts`):单个请求的完整闭环。
- `createHMRServer`(`server/hmr.ts`):文件变化如何映射到客户端更新。
- `optimizeDeps`(`optimizer/index.ts`):裸导入为什么会被重写到 `.mini-vite/deps`。
