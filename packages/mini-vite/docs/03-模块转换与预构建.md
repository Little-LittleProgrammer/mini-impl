# 模块转换与预构建

这篇讲两件事:开发态**单个模块**是怎么转换的(`transformRequest`),以及启动时**第三方依赖**为什么要先预构建一遍(`optimizer`)。两者都围绕同一个目标——让浏览器只需处理原生 ESM。

## 一、单模块转换:transformRequest

`transformRequest`(`transformRequest.ts`)是 transform 中间件背后的实际入口。它把插件容器的三个钩子串成一条流水线,并加上缓存。

```ts
export async function transformRequest(url, serverContext, options = {}) {
    const { pluginContainer } = serverContext
    url = cleanUrl(url)                          // 去掉 ?query 和 #hash

    const resolveResult = await pluginContainer.resolveId(url)
    let transformResult = null

    if (resolveResult?.id) {
        const cacheKey = resolveResult.id
        const mtimeMs = await getFileMtimeMs(resolveResult.id)
        const cacheEntry = transformCache.get(cacheKey)

        // 缓存命中且文件未修改 → 直接返回
        if (cacheEntry && cacheEntry.mtimeMs === mtimeMs) {
            return cacheEntry.result
        }

        const loadResult = await pluginContainer.load(resolveResult.id)
        let code = typeof loadResult === 'object' ? loadResult.code : loadResult

        if (typeof code === 'string') {
            transformResult = await pluginContainer.transform(code, resolveResult.id)
            if (transformResult) {
                transformCache.set(cacheKey, { result: transformResult, mtimeMs })
            }
        }
    }
    return transformResult
}
```

### 流程拆解

1. **cleanUrl**:`/src/App.vue?vue&type=style` 这类带 query 的请求,先剥成干净路径再解析。
2. **resolveId**:拿到磁盘上的绝对 id 作为后续所有操作的 key。
3. **缓存检查**:以 id 为 key,以文件 `mtimeMs`(修改时间)为校验依据。文件没动就直接返回上次结果。
4. **load → transform**:加载源码,再走完整 transform 链。
5. **写缓存**:成功后存入 `transformCache`。

### 缓存机制

```ts
interface TransformCacheEntry {
    result: TransformResult
    mtimeMs: number | null
}
const transformCache = new Map<string, TransformCacheEntry>()
```

- **键**:`resolveId` 返回的 id(磁盘绝对路径)。
- **校验**:对比文件 `mtimeMs`。一致才算命中——比单纯"存在即命中"更安全,文件改了就自动失效。
- **失效**:`invalidateTransformCache(id)` 会删掉 id、cleanUrl、normalizePath 三种形态的键(因为同一文件在不同环节可能以不同形态作 key)。HMR 在 `change`/`add`/`unlink` 时调用它。

> 这是**纯内存、基于 mtime** 的缓存,进程重启即清空。真实 Vite 还有基于内容 hash 的文件系统持久缓存。

### 虚拟模块为何不缓存

`getFileMtimeMs` 对非绝对路径(如虚拟模块 id)或不存在的文件返回 `null`。虚拟模块每次 `mtimeMs` 都是 `null`,看似 `null === null` 会命中——但虚拟模块(如 client.js)由 hmr 插件在 load 阶段直接返回内容,通常每次请求重新生成,影响很小。重点记住:**缓存键依赖真实文件的 mtime**。

## 二、为什么需要预构建

浏览器原生 ESM 有两个现实问题,预构建就是来解决它们的:

1. **CommonJS / UMD 不兼容**。很多 npm 包仍以 CJS 发布(`module.exports`),浏览器的 `import` 无法直接消费。必须先转成 ESM。
2. **请求瀑布**。一个像 `lodash-es` 的包内部可能拆成几百个小模块。若不打包,浏览器会为单个依赖发出数百个请求,开发态首屏被拖垮。预构建用 esbuild 把每个依赖**打成一个文件**,请求数从几百降到一。

## 三、预构建流程:optimizeDeps

`optimizeDeps`(`optimizer/index.ts`)在服务器 `listen` 回调里执行,分三步:

```ts
export async function optimizeDeps(config) {
    // 1. 定位入口
    const entry = path.resolve(config.root, 'src/main.ts')

    // 2. 扫描:用 esbuild 跑一遍,靠插件收集裸导入
    const deps = new Set<string>()
    await build({
        entryPoints: [entry],
        bundle: true,
        write: false,                       // 只扫描,不产出
        plugins: [esbuildScanPlugin(deps)],
    })

    // 3. 预构建:把每个裸导入打成独立 ESM 文件
    await build({
        entryPoints: [...deps],
        write: true,
        bundle: true,
        format: "esm",
        splitting: true,
        outdir: path.resolve(config.root, 'node_modules/.mini-vite/deps'),
        platform: 'browser',
        target: 'esnext',
        mainFields: ['module', 'browser', 'main'],
        conditions: ['module', 'browser', 'import'],
        define: {
            'global': 'globalThis',
            'process.env.NODE_ENV': '"development"',
        },
    })
}
```

### 扫描阶段:esbuildScanPlugin

扫描的精髓在于**借 esbuild 走一遍依赖图,但什么都不真正打包**——用 `onResolve` 钩子拦截,把裸导入记下来后标记 `external` 跳过:

```ts
export function esbuildScanPlugin(depImports: Set<string>): Plugin {
    return {
        name: 'mini-vite:dep-scan',
        setup(build) {
            // 样式/图片/.vue 等非 JS 资源:标记 external,不让 esbuild 处理
            build.onResolve(
                { filter: new RegExp(`\\.(${externalTypes.join("|")})$`) },
                (info) => ({ path: info.path, external: true })
            )
            // 裸导入(第三方依赖):记录后标 external
            build.onResolve(
                { filter: /^[\w@][^:]/ },
                (info) => {
                    depImports.add(info.path)
                    return { path: info.path, external: true }
                }
            )
        },
    }
}
```

- 正则 `/^[\w@][^:]/` 匹配裸导入(`vue`、`@vue/runtime-core`),排除相对路径和 `C:\` 这类。
- `externalTypes`(`constants.ts`)列出 css/less/scss/vue/svelte/jsx/tsx 等,这些被标 external 直接跳过,避免 esbuild 碰到不认识的资源类型报错。

### 预构建阶段

把扫描得到的 `deps` 集合当作 entryPoints 交给 esbuild,输出到 `node_modules/.mini-vite/deps/`。关键配置:

| 配置 | 作用 |
| --- | --- |
| `format: 'esm'` | 输出原生 ES 模块 |
| `bundle: true` | 把依赖内部的多文件打成一个 |
| `splitting: true` | 多个依赖共享的代码抽成公共 chunk |
| `mainFields` / `conditions` | 优先选包的 ESM 入口 |
| `define` | 替换 `global`、`process.env.NODE_ENV` 等浏览器没有的标识 |

## 四、产物如何被消费:路径重写

预构建产物落在磁盘上还不够,得让浏览器请求到它。这一步由 `importAnalysis` 完成(见 [插件系统](./02-插件系统.md)):

```js
// 源码
import { createApp } from 'vue'

// importAnalysis 重写后
import { createApp } from '/node_modules/.mini-vite/deps/vue.js'
```

之后浏览器请求 `/node_modules/.mini-vite/deps/vue.js`,经 resolve 插件 `path.join(root, url)` 定位到磁盘上的预构建产物,直接返回。

整条闭环:

```
optimizeDeps 启动时打包    →    node_modules/.mini-vite/deps/vue.js
                                          ↑
importAnalysis 重写 import  →  指向上面这个产物
                                          ↑
浏览器请求该路径            →  resolve 定位磁盘文件并返回
```

## 五、当前实现的简化

| 方面 | mini-vite | 真实 Vite |
| --- | --- | --- |
| 触发时机 | 每次启动全量重跑 | 按需 + 锁文件 hash 判断是否复用 |
| 缓存 | 无,每次重新打包 | `_metadata.json` 记录 hash,命中则跳过 |
| 入口 | 写死 `src/main.ts` | 从 HTML、配置多入口扫描 |
| 增量 | 无 | 运行中发现新依赖会重新优化并刷新 |

完整对比见 [与 Vite 的差异](./05-与Vite的差异.md)。
