# 插件系统

插件系统是 mini-vite 最核心的抽象。开发服务器本身只负责拦截请求,真正"把一个文件变成浏览器能跑的代码"的工作,全部由插件完成。这套设计直接借鉴 Rollup 插件 API。

## 一、插件接口

mini-vite 的 `Plugin` 接口(`plugin.ts`)继承自 Rollup 的 Plugin,但只实际使用这几个钩子:

```ts
export interface Plugin extends RollupPlugin {
    name: string
    // 配置开发服务器:拿到 serverContext 引用并保存
    configureServer?: ServerHook
    // 解析模块 id:把请求路径变成可加载的 id
    resolveId?: (id: string, importer?: string)
        => Promise<PartialResolvedId | null> | PartialResolvedId | null
    // 加载模块内容:返回源码字符串
    load?: (id: string) => Promise<LoadResult | null> | LoadResult | null
    // 转换模块内容:把源码改写成另一种形式
    transform?: ObjectHook<...>
    // 转换 HTML(预留扩展点,内置插件未实现)
    transformIndexHtml?: (raw: string) => Promise<string> | string
}
```

`pluginContainer.ts` 顶部的注释列出了完整的 Vite/Rollup 钩子(`config`、`buildStart`、`renderChunk` 等),但 mini-vite **只实现了 `resolveId`、`load`、`transform` 这三个开发态最高频的钩子**,加上 `configureServer` 和预留的 `transformIndexHtml`。

这三个钩子的分工正好对应转换的三个阶段:

| 钩子 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- |
| `resolveId` | 请求路径 + importer | 模块 id | 路径 → 可定位的 id |
| `load` | 模块 id | 源码字符串 | id → 内容 |
| `transform` | 源码 + id | 新源码 | 内容 → 改写后的内容 |

## 二、插件容器

`createPluginContainer`(`pluginContainer.ts:95`)是钩子的调度中心。注意它是一个**工厂函数返回的普通对象**,不是 class。它负责把多个插件的同名钩子按规则串起来。

### resolveId:首个返回非空即停止

```ts
async resolveId(id, importer?) {
    const ctx = new Context()
    for (const plugin of plugins) {
        if (plugin.resolveId) {
            const newId = await plugin.resolveId.call(ctx, id, importer)
            if (newId) {
                id = typeof newId === 'string' ? newId : newId.id
                return { id }   // 第一个返回非空的插件胜出,立即停止
            }
        }
    }
    return null
}
```

这是 **first-non-null** 模式:按插件注册顺序依次尝试,谁先返回结果就用谁的,后面的插件不再执行。所以 `resolvePlugin` 放在数组第一位——它兜底处理绝对/相对路径。

> 这里是**串行 for 循环**,不是 `Promise.all` 并行。resolveId 的语义本身要求按顺序短路,无法并行。

### load:同样 first-non-null

```ts
async load(id) {
    const ctx = new Context()
    for (const plugin of plugins) {
        if (plugin.load) {
            const result = await plugin.load.call(ctx, id)
            if (result) return result   // 第一个能加载的胜出
        }
    }
    return null
}
```

`esbuildPlugin` 加载 JS、`cssPlugin` 加载 CSS、`hmrPlugin` 加载虚拟客户端模块,各管各的文件类型,互不冲突。

### transform:链式累积

transform 和前两个不同,它是**管道**——每个插件的输出是下一个插件的输入:

```ts
async transform(code, id) {
    const ctx = new Context()
    for (const plugin of plugins) {
        if (plugin.transform) {
            let result = null
            // 兼容 ObjectHook 形式 { handler, order }
            if ('handler' in plugin.transform) {
                result = await plugin.transform.handler.call(ctx, code, id)
            } else {
                result = await plugin.transform.call(ctx, code, id)
            }
            if (!result) continue              // 返回 null 表示不处理,code 不变
            if (typeof result === 'string') {
                code = result
            } else if (result.code) {
                code = result.code             // 用输出覆盖 code,传给下一个插件
            }
        }
    }
    return { code, map: null }
}
```

所以一个 `.ts` 文件流过 transform 链时,`code` 被逐步改写:esbuild 先把 TS 编成 JS,importAnalysis 再在这份 JS 上重写 import。**顺序错了结果就错**——这就是为什么 esbuild 必须排在 importAnalysis 前面。

### 插件上下文 Context

```ts
class Context implements Pick<PluginContext, 'resolve'> {
    async resolve(id: string, importer?: string) {
        let out = await pluginContainer.resolveId(id, importer)
        if (typeof out === 'string') return { id: out } as ...
        return out as ResolvedId | null
    }
}
```

Context 当前只暴露一个 `resolve` 方法。它的意义在于:插件在 transform 内部想解析一个路径时,可以调 `this.resolve()` 复用整条 resolveId 链,而不必自己实现路径解析。`importAnalysis` 处理相对路径时正是这么用的。

## 三、内置插件逐个看

下面六个插件按注册顺序讲,这也是它们在容器里被调用的顺序。

### 1. resolve —— 路径解析(`plugins/resolve.ts`)

只负责**绝对路径和相对路径**,不处理裸导入。

- **绝对路径**(`/src/main.ts`):先看磁盘上存不存在;不存在就拼上 `root` 再试(支持 `/src/xxx` 这种从 root 起算的写法)。找到后还要用 `isFileInsideRoot` 校验,防止越权访问 root 之外的文件。
- **相对路径**(`./foo`):用 `resolve.sync` 基于 importer 所在目录解析。带后缀直接解析;不带后缀则依次尝试 `.ts/.js/.jsx/.tsx/.json` 补全。

```ts
async resolveId(id, importer) {
    if (path.isAbsolute(id)) {
        if (await fse.pathExists(id)) { /* 校验 root 后返回 */ }
        id = path.join(serverContext.root, id)  // 拼 root 再试
        if (await fse.pathExists(id)) { /* ... */ }
        return null
    } else if (id.startsWith('.')) {
        // 相对路径:resolve.sync + 后缀补全
    }
    return null
}
```

> 关键认知:**裸导入(`vue`、`pinia`)不经过 resolve 插件**。它们由 `importAnalysis` 在 transform 阶段直接字符串重写为预构建产物路径。这是 mini-vite 的简化——真实 Vite 的 resolve 插件会完整处理 node_modules 解析、`exports` 字段等。

### 2. esbuild —— 编译 + 加载(`plugins/esbuild.ts`)

身兼 `load` 和 `transform` 两职:

- **load**:`isJsRequest` 为 true 时用 `fse.readFile` 读取源码。这是 JS 类文件的统一加载入口。
- **transform**:正则 `/\.(m?ts|[jt]sx)$/` 匹配 TS/TSX/JSX,调用 `transformWithEsbuild` 编译成 `format: 'esm'` 的 JS,保留 sourcemap。纯 `.js` 不在这里处理。

```ts
async transform(code, id) {
    const reg = /\.(m?ts|[jt]sx)$/
    if (reg.test(id) || reg.test(cleanUrl(id))) {
        const result = await transformWithEsbuild(code, id, {
            target: "esnext",
            format: "esm",
            sourcemap: true,
        })
        return { code: result.code, map: result.map }
    }
    return null   // 非 TS/JSX 文件,交给后面的插件
}
```

### 3. commonjs —— CJS 转 ESM(`plugins/cjs.ts`)

浏览器不认识 `module.exports`/`require`,这个插件用 esbuild 把 CommonJS 转成 ESM:

```ts
async transform(code, id) {
    // 只处理 .js / .cjs,TS/JSX 已被 esbuild 插件处理过
    const jsFileReg = /\.(js|cjs)$/
    if (!jsFileReg.test(id) && !jsFileReg.test(cleanUrl(id))) return null
    if (isESMModule(code)) return null      // 已是 ESM,跳过
    if (!hasCommonJSSyntax(code)) return null // 没有 CJS 语法,跳过

    const result = await transform(code, {
        loader: getLoader(id),
        format: 'esm',
        platform: 'browser',
        target: 'esnext',
        define: {
            'process.env.NODE_ENV': '"development"',
            'global': 'globalThis',
        },
    })
    return { code: result.code, map: result.map }
}
```

判断逻辑靠两个启发式函数:`isESMModule`(含 import/export 就当 ESM)、`hasCommonJSSyntax`(含 require/module.exports/exports. 就当 CJS),两者都会先用 `cleanCode` 剥掉注释和字符串,避免误判。

> 仓库里还有一个 `cjs-theory.ts`,是**手写正则**实现 CJS 转换的"教学版"(含 `transformExportsAssignments`、`require` polyfill 等),用来对照理解 esbuild 内部大致做了什么。它**没有被注册进插件数组**,实际生效的是 `cjs.ts`。

### 4. importAnalysis —— 导入重写 + HMR 注入(`plugins/importAnalysis.ts`)

整条 transform 链里最核心的一环。它用 `es-module-lexer` 解析出所有 import 语句,逐个处理:

```ts
async transform(source, importer) {
    if (!serverContext || !isJsRequest(importer)) return null
    await init                          // es-module-lexer 必须先初始化
    const [imports] = parse(source)
    const ms = new MagicString(source)  // MagicString 做精确字符串替换并生成 sourcemap
    const importees: string[] = []

    for (let info of imports) {
        const { s: modStart, e: modEnd, n: modSource } = info
        if (!modSource) continue
        let resolvedId = modSource

        if (/^[\w@][^:]/.test(modSource)) {
            // 裸导入 → 重写为预构建产物路径
            const bundlePath = normalizePath(
                path.join('/', 'node_modules/.mini-vite/deps', `${modSource}.js`)
            )
            ms.overwrite(modStart, modEnd, bundlePath)
            resolvedId = bundlePath
        } else if (modSource.startsWith('.') || modSource.startsWith('/')) {
            // 相对/绝对路径 → 走 resolve 链,再转成浏览器 URL
            const resolved = await this.resolve(modSource, importer)
            if (resolved) {
                const url = fsPathToUrl(resolved.id, serverContext.root)
                ms.overwrite(modStart, modEnd, url)
                resolvedId = url
            }
        }
        if (resolvedId) importees.push(resolvedId)
    }

    // 上报模块图(给 HMR 算更新边界用)
    const normalizedImporter = normalizePath(fsPathToUrl(importer, serverContext.root))
    serverContext.hmr?.updateModuleGraph(normalizedImporter, importees)

    // 注入 HMR 上下文(client.js 自身除外)
    if (serverContext.hmr && !importer.includes('.mini-vite/client')) {
        ms.prepend(
            `import { createHotContext } from "/node_modules/.mini-vite/client.js";\n` +
            `const __hmr__ = createHotContext("${normalizedImporter}");\n` +
            `import.meta.hot = __hmr__;\n\n`
        )
    }
    return { code: ms.toString(), map: ms.generateMap() }
}
```

三个产物:
1. **改写后的 import 路径**——浏览器才能正确发起后续请求。
2. **更新的模块图**——HMR 据此计算"改了 A,需要更新哪些模块"。
3. **注入的 `import.meta.hot`**——业务代码才能写 `if (import.meta.hot) { ... }`。

详见 [模块转换与预构建](./03-模块转换与预构建.md) 和 [热更新 HMR](./04-热更新HMR.md)。

### 5. css —— CSS 转 JS 模块(`plugins/css.ts`)

`load` 读 CSS 文本,`transform` 把它包成一段 JS:

```ts
async transform(code, id) {
    if (!isCssRequest(id)) return null
    const escapedCss = code
        .replace(/\\/g, '\\\\').replace(/"/g, '\\"')
        .replace(/\n/g, '\\n').replace(/\r/g, '\\r')

    return {
        code: `
const cssStr = "${escapedCss}";
const moduleId = "${id}";
function updateStyle(css, id) {
    let style = document.querySelector(\`style[data-vite-dev-id="\${id}"]\`)
    if (style) { style.innerHTML = css }
    else {
        style = document.createElement("style")
        style.setAttribute("data-vite-dev-id", id)
        style.innerHTML = css
        document.head.appendChild(style)
    }
    return style
}
updateStyle(cssStr, moduleId);
if (import.meta.hot) {
    import.meta.hot.accept(() => {})
    import.meta.hot.dispose(() => { /* 移除 style 标签 */ })
}
export default cssStr;`.trim(),
        map: null,
    }
}
```

返回的是 JS,所以浏览器拿到的 `Content-Type` 是 JS——CSS 被"伪装"成模块,从而能复用 ESM 的加载和 HMR 通道。

> 仅做**转义注入**,不支持 CSS Modules、PostCSS、Sass/Less 等。这些能力的对比见 [与 Vite 的差异](./05-与Vite的差异.md)。

### 6. hmr —— 提供客户端虚拟模块(`plugins/hmr.ts`)

它不转换业务代码,只做一件事:让 `/node_modules/.mini-vite/client.js` 这个虚拟路径可被加载。

- **configureServer**:用 esbuild 把 `client/client.ts`(TypeScript)编译成 JS,存进闭包变量 `clientCode`。会按几个候选路径查找客户端源码以适配开发/安装两种场景。
- **resolveId**:命中固定路径 `/node_modules/.mini-vite/client.js` 时返回该 id(标记为虚拟模块)。
- **load**:命中时返回缓存的 `clientCode`。

这样浏览器就能像加载普通模块一样加载 HMR 运行时,而它实际并不存在于磁盘。

## 四、写一个自己的插件

照着接口实现对应钩子即可。一个最小示例:

```ts
import { Plugin } from '../plugin'

export function myPlugin(): Plugin {
    let serverContext
    return {
        name: 'my-plugin',
        configureServer(server) {
            serverContext = server   // 需要 server 引用就在这里存
        },
        async transform(code, id) {
            if (!id.endsWith('.special')) return null  // 不处理就返回 null
            return { code: doSomething(code), map: null }
        },
    }
}
```

要点:
- 不处理当前文件时**返回 `null`**,容器会跳过它继续走下一个插件。
- 需要解析路径时调 `this.resolve(id, importer)`,复用整条 resolve 链。
- 注册位置(在 `server/index.ts` 的 plugins 数组里的顺序)决定它在 transform 链中的执行时机,谨慎选择。
